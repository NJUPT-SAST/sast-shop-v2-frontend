# 移动端 Mock 设计与交互核查

## 核查范围与结论

基于当前 frontend main `1abd6e3`，使用 fauxrpc 样例数据核查商城、商品详情、下单与支付弹层、订单列表与详情、团购、采购任务、个人中心、地址簿和上架表单。主视口 390×844，补查 320×568 和 428×926。未测试真实飞书扫码、真实支付和上传，也未验证数据库持久化。

整体是可用的商城界面，商品、价格、状态和主操作层级明确。优先改进错误恢复和操作识别；基础布局没有必要整体重做。

## 做得好的部分

1. 商品列表在 320 和 390 宽度下保持两列，价格与商品名有清晰层级，图片失败时显示自定义占位。
2. 商品详情和地址抽屉在矮屏上可以滚动；主操作保持可达，没有发现稳定状态下的明显横向溢出。
3. 订单详情集中展示订单号、金额、付款标识等信息；上架表单支持条码匹配和参考价格，减少重复输入。

## 优先问题

### 1. [P1] 地址保存失败时，当前表单没有错误提示

**证据：浏览器已复现。** 地址簿 → 新建地址 → 不填写收件人 → 保存，表单内没有任何错误；取消回到地址簿后才看到“收件人不能为空”。截图：`/tmp/sast-shop-audit-address-error.jpg`。

原因是 `profile-dialogs-provider.tsx:292` 的 mutation 统一写入错误，而错误只在地址簿和收款码抽屉渲染。地址编辑抽屉打开时地址簿已经关闭，编辑抽屉没有错误区。删除确认同样需要覆盖失败反馈，但本次没有模拟删除失败。

**影响：** 用户无法判断是漏填、网络失败还是按钮无效，可能反复点击。

**调整：** 在字段旁显示校验错误并聚焦首个错误字段；接口错误放在当前表单抽屉；保留输入，保存中展示状态并防止重复提交。

建议命令：`$impeccable harden`。

### 2. [P1] 飞书扫码取消或鉴权失败后，上架入口可能只剩空页面

**证据：源码确认，未在真实飞书设备复现。** `publish-spot-form.tsx:292` 在取消扫码时直接返回，其他失败只 toast；当入口是 scan、飞书 UI 开启、条码为空且扫描结束时，`showEntryForm` 为 false。扫描提示消失后没有重试或手动输入入口。

普通浏览器无 SDK 时有手动输入降级，本次浏览器可正常使用该路径；问题限定在 SDK 存在后的失败分支。

**影响：** 用户主动取消扫码或遇到鉴权失败后，不知道如何继续上架。

**调整：** 取消或失败后显示“重新扫码”和“手动输入条码”；鉴权错误提供明确恢复说明。

建议命令：`$impeccable harden`。

### 3. [P2] 订单视角悬浮按钮缩写难懂，还会遮挡订单内容

**证据：390×844 浏览器截图确认。** `orders-view.tsx:606` 的圆形按钮用“买/卖”或“拼/团”表达角色；完整说明主要在 title 属性中。按钮位于列表右下方，覆盖了订单卡片的部分文字和状态。截图：`/tmp/sast-shop-audit-orders.jpg`。

**影响：** 新用户可能不知道自己在查看哪类订单；移动端无法依赖悬停解释。

**调整：** 在筛选区提供“我购买的 / 我售出的”和“我的拼单 / 团长任务”分段控件，明确当前视角，移除列表上的浮动遮挡。

建议命令：`$impeccable clarify`、`$impeccable layout`。

### 4. [P2] 采购记录依赖手势和图标，部分购买容易被误解

**证据：浏览器确认。** `errand-purchase/shopping-task-view.tsx:550` 的展开区使用勾、减号和叉表示采购结果，减号容易被理解成减数量。展开后商品标题附近的布局也变得拥挤。截图：`/tmp/sast-shop-audit-purchase.jpg`。

**影响：** 首次采购时需要尝试才能知道“部分购买”的含义；记录结果前的判断成本偏高。

**调整：** 展开后直接显示“全部买到 / 部分买到 / 未买到”；保留快捷动作，但补充可见文字与保存中的反馈。

建议命令：`$impeccable clarify`、`$impeccable adapt`。

### 5. [P2] 矮屏支付弹层先看到二维码与确认按钮，金额和标识码在下方

**证据：320×568 浏览器确认。** 二维码占据首屏主体，金额与付款标识码需要滚动才看到，“我已支付”按钮已经固定可见；390×844 下信息可以完整呈现。

**影响：** 用户切换到微信或支付宝前，容易遗漏需要核对的金额和标识信息。

**调整：** 将金额、收款方与付款标识码放在二维码之前；底部确认按钮附近保留简短金额摘要。保持内容滚动和操作按钮固定。

建议命令：`$impeccable adapt`、`$impeccable layout`。

## 不同使用者的风险

- **首次使用者 Jordan：** 订单“买/卖”“拼/团”和采购减号需要猜测，创建店铺图标也缺少可见文字。
- **单手移动用户 Casey：** 矮屏支付需要额外滚动核对金额，订单悬浮按钮占据可读区域；收货地址删除文字按钮应检查是否保持 44px 触控高度。
- **边界测试用户 Riley：** 空地址保存没有当前层错误，飞书取消扫码后缺少恢复路径，容易产生“操作无效”的判断。

这些是基于页面操作与源码的情景评估，没有冒充真人可用性访谈。

## 其他细节与相邻问题

- 上架商品所需收款码在提交后才检查，可提前提示配置状态，减少填写后被中断。
- “上架”加号和“创建店铺”图标已有部分无障碍名称，但对视觉用户仍建议补可见文字；店铺空状态应给明确下一步。
- 地址删除按钮使用 `h-auto` 和较小纵向 padding，应调整触控区域。未实际量测最终高度，不作为已确认无障碍失败。
- 采购确认金额计算将缺失 `actualUnitPriceCents` 视为 0。若该阶段允许未核价，应显示“待核算”，避免出现具有误导性的零元合计。源码确认；未构造缺价格响应复现。
- 团购页先取 page1、pageSize2，再过滤活动任务；若前两条均结束，后续活动任务可能不出现在预览。源码确认；应按活动状态查询或在服务端筛选后分页。
- 本次团购加载失败来自静态 mock 的分页数量不匹配：请求 2 条，stub 返回 5 条。已在 `/tmp/sast-shop-audit-stubs` 添加分页匹配覆盖以继续视觉核查，未改业务源码，不能把这个失败当成真实后端缺陷。
- 当前实际 DESIGN 与主题使用 Coral 色系；本次未改色彩，也没有在未测量的情况下宣称文本对比度不合格。

## 认知负担与操作感受

主要负担来自需要猜含义的图标和缩写，以及付款时需要上下滚动对照的信息。常规页面没有发现明显超过四项的同级决策堆叠；订单状态筛选属于熟悉业务选项，不需要仅为减少数量而删减。

顺利路径的反馈较清楚，最明显的体验低点是地址保存无提示和扫码异常后的空白。先修这两类反馈，再调整角色切换与采购动作，比全面修改卡片外观更直接改善任务完成率。
